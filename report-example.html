рисков.

Сводка переводит технические наблюдения в последствия для продукта и порядок действий. В этих примерах нарушаются две разные границы доверия.

02 / Границы результата

Что входит в проверку

Отчёт описывает проверенные системы, роли, операции и ограничения. По нему должно быть понятно, на какие области распространяются выводы.

ОбластьЧто рассматривается в образцеЧто фиксируется в проекте
Web / APIДоступ к документам между организациями.Приложения, версии, роли, операции и тестовые учётные записи.
AI / RAGВлияние внешнего документа на вызов инструмента.Модель, источники знаний, инструменты и права пользователя.
Повторная проверкаКритерии подтверждения исправлений.Версия после исправления, повторённые сценарии и итоговый статус.
За пределами образцаСеть, облачная инфраструктура, социальная инженерия и нагрузка.Исключения, недоступные компоненты и ограничения методов.

Фактическое покрытие в рабочем отчёте отделяется от согласованного плана: недоступная функция или непроверенная роль остаются отмеченными как ограничения.

Web / API · Разграничение доступа

DEMO-01 / ОБРАЗЕЦ

Доступ к чужим
документам.

Пользователь одной организации получает документ другой. Приложение проверяет вход в систему, но пропускает проверку права на конкретный объект.

Условная система
app.example
Исходный доступ
Обычная учётная запись
Нарушенная граница
Изоляция организаций

Влияние на бизнес

Ошибка создаёт путь к клиентским документам за пределами разрешений. Возможный ущерб зависит от чувствительности документов, доступных операций и количества объектов. Возможность чтения сама по себе не доказывает возможность изменения или удаления — эти действия проверяются отдельно.

Контекст и путь к результату

Учётная запись A→API документов→Документ организации B

Необходимые условия

  • Две организации используют одно приложение.
  • Обычный пользователь может обращаться к API документов.
  • Документы должны быть разделены по организациям.

Что подтверждает нарушение

  • Целевой документ принадлежит организации B.
  • У пользователя A нет разрешения на него.
  • Ответ содержит данные документа, а не только иной код состояния.

Запись доказательства

Пользователь
DEMO_USER_A · роль «Чтение»
Организация
DEMO_TENANT_A
Целевой объект
DEMO_DOCUMENT_B
Владелец объекта

ОжидаетсяСервер отклоняет обращение к чужому документу и не возвращает его содержимое.

Наблюдение в сценарииОтвет содержит документ организации B при использовании учётной записи организации A.

В рабочем отчёте к записи прилагаются запрос и ответ с безопасными идентификаторами, версия системы, время проверки и условия повторения.

Логика воспроизведения

  1. Подготовить согласованные тестовые организации и документы с заранее известными владельцами.
  2. Проверить штатное чтение своего документа и отсутствие разрешения на чужой.
  3. Обратиться к тестовому чужому объекту с правами пользователя A.
  4. Сопоставить фактические данные ответа с владельцем объекта и сохранить доказательство.

План исправления

  • Проверять права на сервере при каждом обращенииРешение о доступе должно учитывать пользователя, действие, объект и организацию.
  • Брать контекст доступа из доверенного источникаПереданное клиентом значение организации не должно само по себе давать доступ.
  • Закрыть аналогичные путиПроверить чтение, выгрузку и другие согласованные операции с тем же типом объектов.
  • Закрепить границу регрессионной проверкойДобавить сценарии для разных ролей и организаций, включая отказ при отсутствии разрешения.

Критерии ретеста

  • Чужой документ не возвращается через согласованные точки доступа.
  • Разрешённое чтение своего документа продолжает работать.
  • Граница сохраняется для согласованных ролей и связанных операций.
  • Исправление проверено на указанной версии приложения, результат связан с DEMO-01.

AI / RAG · Права инструментов

DEMO-02 / ОБРАЗЕЦ

Подмена инструкций
и права агента.

Документ из базы знаний меняет поведение агента. Инструмент принимает сформированный агентом запрос без независимой проверки прав пользователя.

Условная система
assistant.example
Исходный доступ
Чтение данных своей команды
Нарушенная граница
Источник знаний → действие

Влияние на бизнес

Недоверенный источник может стать причиной действия вне разрешений: запроса чужих данных или изменения объекта. В образце зафиксировано принятие неразрешённого запроса тестовым инструментом. Фактический экспорт и передача данных не моделируются.

Контекст и путь к результату

Внешний RAG-документ→AI-агент→Инструмент экспорта

Пользователь просит сводку по своей команде. Агент читает внешний документ через RAG и имеет доступ к инструменту экспорта. Документ должен оставаться источником данных; его содержимое не даёт пользователю дополнительных прав.

Решение инструмента
Запрос принят без проверки роли

ОжидаетсяИнструмент проверяет пользователя, действие и область данных до выполнения. Запрос вне прав отклоняется.

Наблюдение в сценарииВнешняя инструкция влияет на вызов. Проверка разрешения на стороне инструмента отсутствует.

В рабочем отчёте связываются версия источника, контекст роли, трасса вызова, параметры и итог выполнения. Намерение модели, принятый вызов и совершённая операция фиксируются отдельно.

Что нужно воспроизвести

  1. Зафиксировать модель, настройки агента, источники RAG и доступные операции.
  2. Выполнить штатную задачу с тестовыми данными и ограниченной ролью.
  3. Проверить согласованный сценарий влияния внешнего документа на вызов инструмента.
  4. Сопоставить запрошенное действие с правами пользователя и решением инструмента.

Для недетерминированного поведения в отчёте нужны условия и наблюдения отдельных прогонов, а также различия между ними.

План исправления

  • Проверять разрешения вне моделиНа стороне инструмента сопоставлять пользователя, операцию и ресурс. Отсутствие разрешения должно останавливать выполнение.
  • Ограничить права агентаОставить сервисной учётной записи только необходимые операции и области данных.
  • Контролировать параметры и последствияПроверять область действия запроса до выполнения; отдельно согласовать подтверждение чувствительных операций.
  • Отделить источники знаний от управляющих инструкцийНедоверенный контент не должен менять правила доступа. Эта граница должна сохраняться независимо от ответа модели.

Критерии ретеста

  • Инструмент отклоняет вызов вне прав, даже если агент сформировал его.
  • Нет побочного действия до проверки разрешения.
  • Штатная задача выполняется в пределах роли пользователя.
  • Согласованные вариации источников, ролей и ресурсов не расширяют доступ.
  • В отчёте указаны версии модели, приложения и настроек, на которых повторялись сценарии.

05 / После исправления

Результат ретеста

Ретест отвечает на конкретный вопрос: изменился ли результат ранее подтверждённого сценария. Для каждой находки фиксируются версия системы, проверенные условия и один из статусов.

Исправлено
Сценарий больше не воспроизводится, согласованные связанные проверки пройдены. Указаны условия и границы вывода.
Исправлено частично
Часть пути закрыта, но остаётся вариант воспроизведения или непокрытая часть согласованного исправления.
Воспроизводится
После изменений нарушение сохраняется. Приведено актуальное доказательство на новой версии.
Не удалось проверить
Нет необходимого доступа, компонента или условия. Указана причина; такой статус не означает исправление.

06 / Для работы команды

Что получает
команда.

  1. Сводка для принятия решений

    Основные риски, приоритет исправлений и ограничения проверки. Основа для решения о выпуске, сроках и распределении ресурсов.

  2. Находки для разработки

    Идентификатор, затронутая область, условия, доказательства, влияние, рекомендации и критерии приёмки исправления.

  3. Карта покрытия

    Проверенные системы, роли и сценарии. Недоступные участки и исключения видны отдельно от выполненных работ.

  4. Обновление после ретеста

    Связь каждого повторного наблюдения с исходной находкой, версией исправления и итоговым статусом.
